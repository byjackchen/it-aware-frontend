# ServiceNow CSAT and SSC timezone contract

## ServiceNow monthly quality

Both endpoints require the existing survey-batch and incident read permissions. `batch_oid` is a survey batch OID. `timezone` is an IANA timezone name, defaults to `UTC`, and returns HTTP 422 when invalid. An unknown `batch_oid` returns HTTP 404.

| Endpoint | Required query parameters | Response |
| --- | --- | --- |
| `GET /dashboards/survey-analytics/servicenow-quality` | `batch_oid`, `start_month`, `end_month` (`YYYY-MM`); six optional metric-specific date parameters described below | `batch_oid`, selected date bases, `months[]`, `averages` |
| `GET /dashboards/survey-analytics/servicenow-month-details` | `batch_oid`, `month` (`YYYY-MM`); optional `scope` (`all`, `csat`, `poor`, `feedback`), `part` (`denominator` or `numerator` for rate scopes), `denominator_date`, `numerator_date`, `page` (1-based), `rated_only`, repeated `ratings` (1–5) | `month`, `ticket_count`, `assessment_count`, `filtered_ticket_count`, `tickets[]` |

The monthly range is inclusive by month. CSAT and both rate denominators use the ServiceNow OIT report ticket scope: assignment group is `OIT SSC`, assignment group contains `OIT Support`, **or** `sys_tags` contains `OIT SSC Tag`, with tickets tagged `Invalid` excluded. These ticket scopes do not require the incident's current state to be `Closed`. Poor and feedback numerators still count assessments on currently `Closed` ServiceNow incidents. All scopes apply the caller's incident read permissions. The backend converts local month boundaries to UTC `[start, end)` bounds. For example, `2026-07-01T02:00:00Z` belongs to June in `America/Los_Angeles` and July in `UTC`. With `Asia/Shanghai` and `opened` denominators, the local September 2026 dump has 617 tickets in July and 744 in August.

The dashboard sends `csat_numerator_date` for rating points and `csat_denominator_date` for valid rating count. Both default to `opened`; Settings offers `opened` and `taken_on` independently for each. Choosing different bases can produce a nonstandard ratio outside the 1–5 range. The backend also accepts `closed` for existing API clients. Poor rate uses `poor_numerator_date` (all three choices, default `taken_on`) and `poor_denominator_date` (`opened` or `closed`, default `opened`). Feedback rate similarly uses `feedback_numerator_date` and `feedback_denominator_date`. The older `csat_date`, `numerator_date`, and `denominator_date` parameters remain fallbacks for existing API clients.

The dashboard sends `opened` for the feedback numerator by default and fixes both poor and feedback denominators to `opened`. The feedback numerator month remains selectable in Settings. Both denominator month selectors are absent from Settings. The endpoint still accepts explicit `closed` denominator dates for existing API clients; omitted parameters default to `opened`.

All numerators use imported `s.status = 'submitted'` assessments from the chosen batch. CSAT applies the OIT report ticket scope; poor and feedback rates require a currently Closed ServiceNow incident. For `opened` or `closed`, all imported valid ratings count, including repeated imported rows for one assessment ID. `taken_on` uses the actual Table API timestamp; only completed source assessments have one. `feedback_count` and `poor_count` count distinct incident OIDs, while `rating_count` and `rating_sum` count each imported row. Poor and feedback date selectors may yield different numerator and denominator cohorts in the same month.

Each `months[]` entry contains `month`, `ticket_count` (a compatibility alias of `feedback_ticket_count`), `poor_ticket_count`, `feedback_ticket_count`, `feedback_count`, `rating_count`, `rating_sum`, `poor_count`, `csat`, `poor_rate`, and `feedback_rate`. `averages` contains the simple average of non-null monthly metric values. The frontend monthly table can show values or complete calculations. Detail `tickets[]` contain the incident identity, title, state, opened/closed instants, caller, assigned group, and imported `assessments[]` with `submitted_at`, optional `source_taken_on`, rating, questions, and answer. Stored timestamps remain absolute instants; the frontend renders them in the selected timezone.

The detail view defaults to `scope=all` and `denominator_date=closed`, preserving its previous ticket list and the rated-only, score, and Apply filters. `csat` shows the valid-rating cohort from the chart, with no numerator/denominator toggle: `ticket_count` is distinct tickets and `assessment_count` is valid rating rows, so the two may differ. `poor` and `feedback` default to `part=denominator`, using the OIT report ticket filter and `opened` month; `part=numerator` uses the chart's current numerator date, currently Closed ticket scope, and imported assessment conditions. Poor numerator assessments must be rated 1–3; feedback numerator assessments need only be submitted. These numerator lists count distinct tickets, while `assessment_count` counts matching assessments. `taken_on` filters and attaches only assessments taken in that month. The detail XLSX export downloads every page of the selected month and current scope; for `all`, it applies the rated-only and score filters, and for rate scopes, it follows the numerator/denominator part.

Month details return 50 tickets per page (`page` from 1 to 1,000,000), ordered by the selected ticket date descending (or by closed time for `taken_on`), stable ID, and OID. `ticket_count` and `assessment_count` cover the entire selected scope under the caller's incident permissions; `filtered_ticket_count` counts matching tickets across all pages. The dashboard uses `rated_only` and repeated `ratings` only for the `all` scope. `denominator_date=taken_on` is only valid with `scope=csat`; `part=numerator` requires `scope=poor` or `feedback`. Invalid rating values and month boundaries that cannot be represented in UTC return HTTP 422.

Migration 0127 adds nullable `campaigns.surveys.source_taken_on`. Run `uv run python -m scripts.backfill_servicenow_taken_on` after deploying the migration to enrich existing imported assessments. The regular ServiceNow assessment sync fetches `state` and `taken_on` from `/api/now/table/asmt_assessment_instance` and maintains the column thereafter. `submitted_at` retains its prior imported Created On meaning for compatibility.

## SSC Dashboard list and export

The SSC Dashboard sends `created_at_from/to` for interactions and `effective_at_from/to` for incidents as ISO 8601 datetimes with explicit offsets. Changing timezone preserves the wall-clock filter text and computes new offsets, so list membership and counts can change. In a repeated fall DST hour, an inclusive start uses the earlier occurrence and an inclusive end uses the later occurrence.

`GET /objects/activities/interactions/export.xlsx` and `GET /objects/activities/incidents/export.xlsx` accept an optional `timezone` IANA name (default `UTC`; invalid values return 422). Their timestamp cells are rendered in that zone. The incident export also reads its bare-date filters (`created_at_*`, `source_created_at_*`) and offset-free `effective_at_*` values as days and wall times in that zone. The export receives the same offset-bearing date range as the corresponding list; changing the display zone does not rewrite stored timestamps.
